Introduction

This Roadmap captures the high level objectives that the Astropy Project aims to achieve to improve the health and stability of the Project, together with the key results we will use to measure progress towards each objective. It is maintained by the Strategic Planning and Organizing Committee (SPOC) and is revisited at least once a year at the Astropy coordination meeting, and at any time via pull requests to this repository.

The Roadmap is used to prioritize the allocation of Project resources. In particular, funding requests submitted in response to the Project's funding calls are asked to identify which key results they address.

How to read this document

Each objective is a qualitative goal that describes a state we want the Project to reach. Each objective has up to five key results: concrete, measurable outcomes that, taken together, tell us whether the objective has been achieved. A key result is a single sentence that contains its own measure of success, for example a number, a published document, or a merged and released feature.

Every objective has an identifier such as O3 and every key result has an identifier such as R3.2. Identifiers are stable: once assigned they are never renumbered or reused, so they can be cited in funding requests, issues, and pull requests without ambiguity. New objectives and key results take the next unused number.

The objectives and key results are defined in roadmap.yaml, and changes to their wording or priority are made by pull request to that file. This document is generated from it and from the GitHub issues that track progress: one issue per objective, linked from the line under its heading, with one sub-issue per key result, linked from the end of the key result. Status updates, links to funded work, and links to implementation pull requests belong in the issues. A key result is complete when its issue has been closed, and an objective is complete when the SPOC closes its issue, after which it is listed under completed objectives below. An entry that no longer applies is removed from the YAML file, which closes its issue; its identifier is not reused.

Each objective may carry a priority (high, medium, or low) assigned by the SPOC. Priority reflects how important the SPOC considers it that progress is made before the next revision, independent of whether anyone is currently working on it.

Objectives

O1 Improve support for reading and writing ASDF files, optionally with GWCS coordinates, in the astropy core and coordinated packages

0/3
  • R1.1Publish a table listing, for the core and coordinated packages, every function and method that accepts FITS files as input or output, either as filenames or as HDU objects, and whether it also accepts ASDF filenames or objects.
  • R1.2Publish a list of the cases where support for ASDF and GWCS is not currently possible without significant upstream work in astropy, asdf-astropy, or the ASDF standard.
  • R1.3Add support for ASDF and GWCS in at least 90% of the remaining cases where this is technically feasible given the current ecosystem.

O2 Develop and implement a modern and maintainable strategy for FITS that improves performance and capabilities

0/5
  • R2.1Publish an APE outlining the plan to improve the performance and long-term maintainability of FITS support within the Astropy Project.
  • R2.2Develop a set of benchmarks that encapsulate the performance targets we want to achieve, for example constant time to open files as file sizes grow.
  • R2.3Make astropy's FITS support competitive with other packages as measured by the benchmarks in R2.2.
  • R2.4Increase the number of active FITS maintainers to at least two and decrease the mean age of open FITS-related issues by one month.
  • R2.5Ensure that new FITS-related issues receive a response within one release cycle.

O3 Provide support for reading and writing spectra using the IVOA SpectrumDM in specutils

0/3
  • R3.1specutils can read any SpectrumDM-compatible VOTable, demonstrated using at least one spectrum downloaded from each of at least two different archives.
  • R3.2specutils can write a Spectrum object to a SpectrumDM-compliant VOTable given sufficient metadata, including validation that gives feedback to the user when the metadata is insufficient.
  • R3.3Reading and writing as in R3.1 and R3.2 are demonstrated, including validation, for both the FITS and the XML serializations specified by SpectrumDM.

O4 Make astropy.units.Quantity a modern part of the Python array ecosystem by supporting any array-API-compliant backend

0/5
  • R4.1A new Quantity class that wraps any array-API-compliant array is merged to main with a stable, documented public API, building on the existing prototype.
  • R4.2The Quantity test suite runs in CI against NumPy and at least three other backends, including array-api-strict with a non-CPU device, with at least 90% of the suite passing for each.
  • R4.3All core array-API operations on Quantity, including arithmetic, ufuncs, indexing and broadcasting, produce correctly unit-propagated results for every tested backend.
  • R4.4Every Quantity behaviour that assumes NumPy array internals and conflicts with array-API compliance is deprecated, each with a migration note in the changelog.
  • R4.5An "Array backends" guide is published in the astropy documentation with end-to-end worked examples for each supported backend, covering unit-aware computation and device transfer.

O5 Provide supported, public ways of serializing astropy objects

0/3
  • R5.1Publish a list of astropy classes together with whether, and how, each can currently be serialized.
  • R5.2Decide on and document a single supported serialization approach, taking into account the existing representation dictionaries in astropy core, astropydantic, and the pydantic integration in stellarphot.
  • R5.3Implement the chosen approach for every class in the list from R5.1 that is not already covered.

O6 Improve the robustness and reliability of performance benchmarking

0/3
  • R6.1Set up a GitHub self-hosted runner on dedicated hardware, where benchmarks can be bound to a specific core, with full documentation of how it was set up.
  • R6.2Switch the astropy core benchmarking job to this runner and demonstrate stable timings in line with local dedicated hardware.
  • R6.3Document how to set up similar benchmarking jobs in other packages in the astropy organization and advertise this to coordinated package maintainers.

O7 Increase the visibility and usage of coordinated packages beyond the core package

0/4
  • R7.1Make it possible to install groups of ecosystem packages by use case, for example pip install astropy[photometry] or pip install astropy[spectroscopy].
  • R7.2The astropy.org landing page highlights the ecosystem and lets visitors navigate coordinated and affiliated packages by use case or domain rather than only presenting the core package.
  • R7.3Usage metrics, such as web analytics on documentation pages, are tracked for every coordinated package.
  • R7.4Monthly documentation traffic for at least three coordinated packages is 50% higher than when tracking started.

O8 Identify the barriers to making Astropy work easily in non-cloud HPC contexts

0/4
  • R8.1Review and categorize the HPC-related issues already reported across the astropy organization.
  • R8.2Develop and carry out a survey of HPC users to identify the challenges they face when using Astropy.
  • R8.3Every barrier identified in R8.1 and R8.2 has an open issue in the relevant repository.
  • R8.4Publish a list of major HPC users of Astropy, based on survey responses, who can be consulted on future work.

O9 Identify the barriers to making Astropy work easily in cloud contexts

0/4
  • R9.1Review and categorize the cloud-related issues already reported across the astropy organization.
  • R9.2Develop and carry out a survey of cloud users to identify the challenges they face when using Astropy.
  • R9.3Every barrier identified in R9.1 and R9.2 has an open issue in the relevant repository.
  • R9.4Publish a list of major cloud users of Astropy, based on survey responses, who can be consulted on future work.

O10 Develop a sustainable and recurring mechanism for measuring and understanding the Astropy user and developer communities, and for identifying gaps in the ecosystem for common astronomy tasks

0/4
  • R10.1Establish or assign a committee or designated role with explicit responsibility for tracking the health of the Astropy user and developer communities.
  • R10.2Define a set of community health indicators for both the user and developer communities, covering for example demographics, use cases, needs, contributor statistics, and satisfaction.
  • R10.3Run a user survey on a recurring cadence, for example every two years, that measures the indicators in R10.2 and collects feedback on missing functionality.
  • R10.4Translate the missing functionality identified in R10.3 into new objectives and key results in this Roadmap.

O11 Create a process to identify and ensure progress on longstanding issues that should be high priority

0/3
  • R11.1Establish or assign a committee or designated role with explicit responsibility for identifying longstanding high-priority issues and overseeing progress on them.
  • R11.2Produce an initial list of longstanding high-priority issues and translate them into objectives and key results in this Roadmap.
  • R11.3Review progress on these issues at least yearly at the coordination meeting.
